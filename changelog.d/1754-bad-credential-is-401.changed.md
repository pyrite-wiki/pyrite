- A credential that does not verify now gets 401 where it used to be served as anonymous: with `anonymous_tier` set, a wrong, empty, expired or revoked API key (`X-API-Key`, `Authorization: Bearer`, or `?api_key` on REST and the live-update socket) or session cookie is refused on REST, `/mcp` and the live-update socket instead of silently getting the anonymous visitor's access. Only a request with no credential is anonymous. A wrong key next to a valid cookie is refused too. REST now accepts `Authorization: Bearer` carrying an API key or a session token, as `/mcp` and the live-update socket do. Two accepted behaviour changes: a request that carries a Bearer token together with `X-API-Key` is judged by the Bearer token alone (it is read first on REST, `/mcp` and the live-update socket, which share one resolver), so a deployment whose proxy adds its own Bearer token while clients send `X-API-Key` is now refused; and two Pyrite instances on one host share the `pyrite_session` cookie name (browsers do not separate cookies by port), so signing in to one can clear the other's session cookie: the other instance refuses it with 401 and, on REST, clears it, signing the user out there.
