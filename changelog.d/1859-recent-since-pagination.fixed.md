- MCP `kb_recent` and `pyrite recent` now apply `since` before `limit` and answer with the list envelope (`total`, `limit`, `offset`, `has_more`): with `since`, the page holds up to `limit` entries updated at or after it and `has_more` is counted over that filtered set, so paging with `offset` (a new `kb_recent` argument and `pyrite recent --offset`) reaches every changed entry exactly once instead of silently dropping the ones past the limit (#1859).
- `total` from `pyrite list-entries`, MCP `kb_list_entries` and REST `GET /entries` now leaves out archived entries and counts one id in two KBs as two entries, matching the listings those totals describe. Callers that ask "is anything indexed?" — `pyrite search`, `pyrite index embed`, REST search's `INDEX_EMPTY` 503, and the repo-status entry counts — count archived entries too (`count_entries(include_archived=True)`), so an index holding only archived entries is no longer reported empty and rebuilt on every search. Orient and README generation keep excluding archived entries from their displayed totals (#1859, #1860).
- `kb_recent`'s `offset`/`limit` declare `minimum: 0` (and `maximum: 200` on `limit`) in the MCP schema and the envelope echoes the clamped values; the `since` scan runs to the end of the list, so a text-sorted `updated_at` with mixed UTC offsets cannot hide a newer row past an older-looking one, and listings order by `..., id, kb_name` so a tied page edge never repeats or skips a row (#1859, #1860).
