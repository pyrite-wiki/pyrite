`metadata` is not a field (Andon #994, decision A; ADR-0051 amends ADR-0042 decision 6): `metadata.k`, in a file or a request, is a second spelling of field `k`, one level only, the same as an alias. Every update refusal (a managed field, `type`, `id`, `body` as a key, a link item's shape) is decided on the field a path denotes, whatever its spelling, depth or surface (service, MCP `kb_update`, REST `PATCH`/`PUT`, CLI `--field`/`--append`/`--remove`/`--unset`), and a request path is parsed once at the boundary, so a key such as `status_change_log[0]` or `metadata.id` inside the `metadata` envelope is the field it names. A request that names one field at two spellings with different values is refused (the #720 rule, extended from aliases to every spelling). Create refuses a managed field sent inside the `metadata` envelope, on REST `POST`, MCP `kb_create` and the service; a declared field or an alias sent there lands at its own key. A file that spells a field twice is reported: `index health` gains `double_spellings` (`{kb, id, field, spellings}`, status `warning`) and `qa validate` the rule `field_spelled_twice`; an update of that field is refused until one spelling goes, and `qa fix` merges a pair whose values agree into the field's own top-level spelling. The model and the index row read such a file the same way (the field's own name first), and a save through the model keeps both values. `aliases` is its own index column: a read spells it where the file does (never under `metadata` for a top-level `aliases:`), and a wikilink resolves by a top-level alias.
