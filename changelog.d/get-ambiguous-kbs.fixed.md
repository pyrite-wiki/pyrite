- **An entry or task id indexed in more than one KB is refused, not answered from the first KB in config order (#528).** Given without a KB (or with a blank `-k`/`kb`/`kb_name`), an id the index holds in more than one KB you can read answers `AMBIGUOUS` with the KBs in `candidate_kbs`: CLI `get`, `task get`, `task status`, `pyrite-read get`, and `update`/`links suggest`/`links discover` given `-k ""`; MCP `kb_get`, `kb_read_body`, `task_status` and the task-graph tools; the `summarize_entry` and `find_connections` prompts and the `pyrite://entries/{id}` resource, whose JSON-RPC error carries the same fields in `data`; REST entry, blocks, collections and AI routes given a blank `kb` (`409`). Only indexed copies are counted: an id indexed in one KB, with a not-yet-indexed `<id>.md` in another, is answered from the indexed KB, as #753 reads it. A KB you cannot read is never listed and never makes an id ambiguous. Name the KB to choose: `-k`, `kb`, `kb_name`, the new `kb_a`/`kb_b` arguments of `find_connections`, or the new `pyrite://kbs/<kb>/entries/<id>` resource. `pyrite-read get` now reports a refusal's own code (`KB_NOT_FOUND`, `AMBIGUOUS`, ...) and its `suggestion`, where it said `ERROR` for every refusal. REST `GET /api/entries/{id}` without `kb` is refused the same way (`409`, `candidate_kbs`), and every web link to an entry now carries its KB (#910); `GET /api/entries/resolve` refuses an ambiguous id, title or alias too (and takes `kb`, a full name or a shortname, as `GET /api/entries/{id}?kb=` now does), and `links discover`/`suggest` given a blank KB no longer return the source as its own neighbour. One exception: an id indexed in one KB with a not-yet-indexed file in another is answered from the indexed KB until `pyrite index sync` (#857). Extension commands' own lookups are #911.
