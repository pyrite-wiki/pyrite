- **An update changes only the fields it names, byte for byte (ADR-0042; #955, B6 P3a).** `pyrite update`, MCP `kb_update`, REST `PUT`/`PATCH /api/entries/{id}` and every in-process update (tasks, `qa fix`, `sw prioritize`) now apply the request as operations to the file's own text instead of re-rendering the whole frontmatter from Pyrite's model: a title edit changes the title's line and nothing else. Comments, key order, quoting, blank lines, list style, a BOM and CRLF line endings stay as written; an untouched bare `yes` is not re-quoted; an undeclared key is written at the top level where the request names it, never nested under `metadata:` (a key the file already holds under `metadata:` is edited there); a legacy link item keeps its spelling and its extra keys; an alias (`actors`/`participants`) is written under the spelling the file uses. `updated_at` is refreshed only where the file already carries it, in the file's own spelling (the `T` or space separator, a `Z`, an offset or none, the fraction's digits, a date-only value; a quoted string stays quoted and a bare timestamp bare), and never added; a timestamp the request sets (`created_at`, `updated_at`) is written as sent, and one that is no instant is refused. A field refused at the top level (`type`, `id`, `links`, `body`) is refused under `metadata` too, since an update writes such a key at the top level. A request that changes nothing writes nothing: the file's bytes and mtime are untouched and the result says `changed: false`. An update never moves a file (#488): only a file with an `id:` line whose type's folder is templated by a field moves, and an unpinned one reports `not_moved`. Two writers editing different fields at the same moment both land: the file is replaced only if it still holds the bytes the edit was computed on, under the momentary lock in the KB's git directory, and a changed file is re-read and re-applied, up to five times, then refused with `CONFLICT` (409 on REST). A KB outside a git repository is written with compare-before-replace and no lock, and the result says `locked: false`. A `before_save` hook may still refuse an update; what it sets on the entry no longer reaches the file. Frontmatter Pyrite cannot model (a tagged, complex or duplicate key, an anchor on the edited key) is refused with the reason and nothing written (#760); so is a result the index could not store. Dropping a stray `body:` key is no longer a side effect of an update (ADR-0042 decision 7).
