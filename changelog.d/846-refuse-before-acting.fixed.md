A malformed request is refused before anything is written, with an existing error code (#846). A link with a missing, null or blank target, or an empty relation, is `VALIDATION_FAILED` on `pyrite link`, `pyrite create --link`, `links bulk-create` and MCP `kb_link`, and so is a target that is not text (a number, boolean or date: YAML reads an unquoted `yes` as true and `010` as 8), with a hint to quote it rather than a silent conversion; `links bulk-create` used to write a null-target link into the source file and then report the item failed, and now fails that item alone (with `error_code`) and writes the rest. A spec missing `source` or `target` likewise fails that item and the others are written (exit 3), where the whole batch used to be refused. `--link a:b:c` is refused instead of storing relation `b:c`, and a malformed `--link` refuses the create instead of leaving the entry behind. A create, `add` or `import` whose own `links:` holds a link the index cannot store (a null target or relation, or a list or mapping as target, relation, note or kb) is refused instead of being written and ending in `NO_OUTCOME`: the same files `index sync` reports as malformed. Nothing else about a file's own links is judged, so a hand-written file with `target: 2024`, a blank target or `relation: ''` is still added. Replaying a link a file already holds is a no-op when the targets match as text: `pyrite link src 2024` or bulk-create `target: "2024"` against a hand file's `target: 2024` no longer adds a second link (`pyrite link` did on earlier versions). MCP `kb_link`'s reply gives `target_id` and `relation` as strings, as its schema types them. `links check|orphans|asymmetric|batch-suggest|suggest|discover` (and MCP `kb_batch_suggest`, `kb_discover_neighbors`, REST `/api/links/batch-suggest` and `/api/links/discover-neighbors`) answer `KB_NOT_FOUND` for a KB that does not exist instead of an empty result; `links suggest|discover -k <missing KB>` said `NOT_FOUND` before. `links bulk-create` refuses a `target_kb` that does not exist, as `pyrite link --target-kb` always has. `pyrite update` naming no field is `VALIDATION_FAILED` and leaves the file alone. A directory given to `create --body-file`, `update --body-file`, `add` or `links bulk-create` is `VALIDATION_FAILED` naming the path instead of `NO_OUTCOME`; a missing file stays `NOT_FOUND`. Files that already hold such links are not repaired.
