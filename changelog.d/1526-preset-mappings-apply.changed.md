A KB made from the journalism-investigation preset (`pyrite kb add DIR --type journalism-investigation`) now applies the preset's type mappings. `pyrite create -t event` stores the entry as `investigation_event`, and `-t document` stores `document_source`, with no override, on every create surface (CLI `create`, `import`, `add FILE`, MCP `kb_create` and `kb_bulk_create`, REST `POST /api/entries`). Before, both were refused `UNDECLARED_TYPE`. `pyrite orient`, `kb_schema`, the REST schema and orient endpoints and `pyrite-admin schema` now list both pairs under `type_mappings`, where they showed `{}`. The rule: a mapping applies when the KB's `kb.yaml` declares its target (or declares no types), and then only the stored type is checked. `add FILE` with `type: event` writes `type: investigation_event` and leaves the rest of the frontmatter as given. Files already on disk as `event` are not re-typed. `--allow-undeclared` (`allow_undeclared`) no longer changes which type is stored when a mapping applies: `-t event --allow-undeclared` in such a KB stores `investigation_event`, where it stored `event`. A KB that declares neither the core type nor its target (for example one made from the known-entities preset) refuses `create -t event` as before, and a KB that declares `event` but not `investigation_event` still stores `event`.
