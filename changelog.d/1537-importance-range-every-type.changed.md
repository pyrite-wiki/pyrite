- **A write no longer stores an `importance` outside 1 to 10, or one that is not a number, on any entry type.** Until now only `event` entries refused one; every other type stored it, and `pyrite qa validate` then warned about what Pyrite had just written. Now a create, an update that sets it, and `pyrite add` of a file that holds it are refused with `VALIDATION_FAILED` and an `errors` row naming `importance` (`rule: range`, `expected: 1-10`), and no file is written or changed, on the CLI (`-f importance=`) and on MCP `kb_create` / `kb_update`. The range is checked on the number as given, so `10.000001`, `10.5`, `10.9`, `0.5`, `0.99` and `-0.5` are refused too (they were accepted: a decimal was cut to a whole number before the comparison). What changes for a non-event entry: `0`, `11`, `-5`, `99` and 30-digit numbers are refused (they were stored); `update -f importance=high` or `=abc`, and an MCP `kb_update` with a non-number `importance` (including the string `"10.9"` or `"1e1"`), are refused (they wrote the text into the file as given); `true`, `false`, `.inf`, `-.inf`, `.nan`, a list, a mapping and a date count as non-numbers and are refused too, and `true` no longer passes as 1 on an event; `pyrite add` of a file whose `importance` is `high`, `[5]`, `{a: 1}`, `0`, `true`, `.inf`, `10.9` or any other non-number or out-of-range value is refused (it was accepted). A numeric string (`"5"`, `" 5 "`, `"05"`) and a whole-valued float (`5.0`, `10.0`, `1e1`) are accepted, as before. A blank or null `importance:` in a file is absent, not a violation: `pyrite add` accepts it and an update of another field says nothing about it. An MCP `kb_update` with `"importance": null` is accepted on every type (an event used to refuse it) and leaves `importance: null` in the file, which reads as absent; on the command line `-f importance=` and `-f importance=null` are text, not null, and are refused.
- **A value already in a file is kept and reported.** An update of another field on a file whose `importance` is out of range or not a number succeeds and returns a "violation already on disk; kept" warning, and never touches that line. On an event, `.inf` and `-.inf` used to crash that update (`NO_OUTCOME` on the CLI, `INTERNAL` on MCP); they now answer as every other value does. One value still fails: with a 30-digit whole number already in the file, the update rewrites the file and then the index cannot store the number, so the command answers `NO_OUTCOME` (CLI) or `INTERNAL` (MCP) although the file has changed, and the index has no row for the entry. It does the same on 0.26.3 (#1584).
- **Two limits, unchanged:** `create -f importance=high` (or `abc`, `.inf`, `true`, a blank) still stores the default 5 or 1 without saying so, and `update -f importance=5.5` still writes `5.5` as given: a number inside 1 to 10 is accepted whether or not it is whole.
- In a `journalism-investigation` KB the refusal used to come from the plugin as `SCHEMA_VIOLATION` (`SchemaViolationError`, a row with no `rule`); it now comes from the model as `VALIDATION_FAILED` (`ValidationError`), the same answer as every other type (#1537).
