**Every search response says what its page is worth (#668).** `pyrite search` and `pyrite-read search` JSON, MCP `kb_search` and REST `GET /api/search` gain `match` (`strong`, `weak` or `none`) and `match_basis` (the reason, in words), plus `keyword_match` (`all_terms`, `some_terms`, `none`) when a keyword leg ran. `match: none` means the KB does not contain an answer: say so, do not build an answer from the results. **The results are still returned when `match` is `none`**; the verdict tells you what they are worth. `legs_run` at the top level names the legs that ran (`keyword`, `semantic`, both or neither); it is not the per-result `legs`. `none` is only said when the search ran as its mode promises: if the semantic leg did not run (the `[semantic]` extra is not installed, or nothing in the KBs searched is embedded), the verdict is `weak` at worst, `match_basis` says why and `legs_run` shows it. `weak` with no results means the search could not run in full or found nothing strong, not that the KB lacks an answer. Each result the vector leg returned carries `similarity`, the cosine similarity to the query (3 decimal places), the same number on SQLite and Postgres, and each hybrid result carries `legs` (`keyword`, `semantic` or both); a hybrid result both legs returned used to lose its score. `distance` is kept for this release and is backend-specific (L2 on SQLite, cosine distance on Postgres): read `similarity`. The verdict is the same on every page of a query and is computed only from entries the caller may read. Its thresholds are measured for `all-MiniLM-L6-v2`; with another `embedding_model`, `match_basis` says `uncalibrated model <name>` and the vector leg is not judged. The CLI's JSON also gains `warnings` when there are any (they were on stderr only).

Behaviour that changes with it: the query is now embedded by the configured `embedding_model` (it used the default model whatever the config said), and so are entries embedded from the write queue; if you set a non-default model, run `pyrite index embed --force` once. The vector leg's cutoff is a similarity floor of 0.155 on both backends (on Postgres the old cutoff removed nothing). In keyword mode, a page past the end of the matches is now empty instead of being refilled with OR-relaxed results. **Hybrid's keyword leg relaxes to OR when the vector leg cannot run.** Hybrid's keyword leg normally requires every term, because the vector leg supplies the near misses. When the vector leg cannot run (the `[semantic]` extra is not installed, or nothing in the KBs searched is embedded) there is nothing to supply them, so the search is a keyword search in full: if no entry has every term it retries with the terms OR-combined, as `--mode keyword` does. It used to return nothing, on the default mode of `kb_search`, for a query keyword mode answers. A scoped search across all KBs no longer comes back short when nearer entries sit in KBs the caller cannot read: the readable set is applied inside each leg's own query, on SQLite inside the vector search itself, so the rows and the verdict are those of the readable KBs however many nearer entries sit elsewhere. Also on SQLite, candidates are the L2-nearest vectors and are then ordered by cosine, so with an embedding model that does not normalise its output a long vector with a high cosine can be missed (the default model normalises). `pyrite links discover` and the link-suggestion API show a different `score` for a semantic match: it is now the cosine `similarity`, where it was `1 - distance / 2`.

For plugins: **the rows `PluginContext.search_semantic` returns gain `similarity`** (and still carry `distance`). That method now runs a vector search with the configured model; it called a method that did not exist and always fell back to keyword search. **Breaking, for an out-of-tree search backend or a caller of one:** `SearchBackend.search_semantic(embedding, kb_name, limit, max_distance=1.3, ...filters)` is now `search_semantic(embedding, kb_name, limit, min_similarity=0.155, ...filters, kb_names=None)`: `max_distance` is gone (a cosine similarity floor replaces it), `kb_names` is new, every returned row must carry `similarity`, and a backend that could not consider every candidate returns a `SemanticRows` with `capped=True`. `has_embeddings()` is now `has_embeddings(kb_name=None, kb_names=None)`. There is no shim: a backend with the old signatures fails with a `TypeError` on the first semantic or hybrid search, and a caller passing `max_distance=` fails the same way. `EmbeddingService.search_similar` changes in step (`min_similarity`, `kb_names`).
