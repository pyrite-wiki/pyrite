- One registered KB whose `kb.yaml` can be read but does not load no longer stops every command on every KB, and `pyrite serve` and `pyrite mcp` start (#1547). That covers bytes that are not UTF-8, a YAML syntax error, a duplicate key, a document over the YAML limits, nesting deeper than Python's recursion limit, a top level that is not a mapping, and a directory or FIFO where the file should be. The other KBs work as before, including commands that span KBs: `pyrite qa duplicates` and MCP `list_edge_types` leave the KB out and name it in `unreadable_kbs`, and `qa duplicates` exits 3. The broken KB is named in three places:
  - `pyrite kb list` marks it, with `error_code` and the parser's words (`error_detail`);
  - `pyrite index health` lists it under `schema_errors` with `error_code: KB_CONFIG_INVALID` and is `unhealthy`;
  - `pyrite index sync` and `index build` skip it, keep its index rows, name it, and exit 3 (1 when nothing synced).

  Every operation that needs that KB's schema answers the new error code `KB_CONFIG_INVALID`: get, create, update and delete, `kb schema show`/`add-type`/`remove-type`/`set`, a sync or reindex of that KB, and `qa assess`. It is not retryable, and its one fixed message is the same on `pyrite`, `pyrite-read`, `pyrite-admin`, MCP and REST; the parser's words reach the local process only. A running server follows the file: it refuses as soon as `kb.yaml` breaks and serves again as soon as it is repaired. Pyrite never rewrites the file: correct `kb.yaml` by hand, then run `pyrite index sync`. Each `unreadable_kbs` row in a sync result now carries `error_code` too. A `kb.yaml` socket answers `KB_UNREADABLE`. There is no size bound yet: a `kb.yaml` of tens of megabytes slows every command.
