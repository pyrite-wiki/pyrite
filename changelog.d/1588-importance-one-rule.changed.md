- **`importance` now gets one answer on every write: a whole number from 1 to 10 is stored as you sent it, and anything else is refused (#1588).** Until now a create turned the value into a whole number or the default before checking it, and said nothing. **Upgrade note: a create that used to succeed with a changed value is now refused** with `VALIDATION_FAILED` and the `importance` row (`rule: range`), the same row an update gives, and nothing is written. This applies to CLI `create -f importance=`, `pyrite add`, `pyrite import`, MCP `kb_create` and `kb_bulk_create`, and REST `POST /api/entries`. The values that change:
  - `10.7`, which was stored as `10`.
  - `3.9`, which was stored as `3`.
  - `true`, which was stored as `1`.
  - `high`, `abc` or a blank `-f importance=`, which were stored as the default `5`.
- **A CSV import (REST `POST /api/entries/import`, `format=csv`) refuses a row whose `importance` cell is not a whole number from 1 to 10.** It used to store `5` instead, without a word, when the cell did not read as a whole number (`10.7`, `true`, `high`), and it read `+5`, ` 5 ` or `1_0` as numbers. Now the cell's text goes to the same rule. That row is refused and reported beside its title with the `importance` row, and the other rows are still imported, as in a JSON import. An empty cell still means no value. A script that relied on the old default should send a whole number or leave the cell empty.
- **A number that is not whole is refused everywhere.** `5.5`, `3.9`, `10.5` and `0.5` are refused on a create and on an update; an update used to write `5.5` as given.
- **Text counts as a number only when it is plain ASCII digits.** `"7"` and `"05"` are still accepted. `" 5 "`, `" 5\n"`, `"+5"`, `"1_0"` and fullwidth `"１０"` are refused over MCP `kb_create` and `kb_update` (an update used to write them into the file as strings), and over REST. On the command line, `-f` still reads `+5`, `1_0`, `１０` and ` 5 ` as the numbers 5 and 10 before any rule sees them. That parser is the same for every field and is unchanged here.
- **REST `POST`, `PUT` and `PATCH /api/entries` answer as the CLI and MCP do.** `true` used to be stored as `1` on a create and an update; `10.7` got FastAPI's top-level 422. Both now get `VALIDATION_FAILED` with the `importance` row, and nothing is written. An out-of-range number (`99`) now gets the same `VALIDATION_FAILED` answer, not the 422. The OpenAPI document still describes `importance` as an integer from 1 to 10.
- **A file that spells importance under `metadata:` is judged too.** `update -f importance=10.7` on such a file used to write `metadata.importance: 10.7`; it is now refused. A file already holding `metadata: {importance: 10.7}` now gets the "violation already on disk; kept" warning on an update of another field.
- **Values already in a file: what the warning reports.** The update still succeeds and the line is never rewritten. Now reported as kept: a `!!binary` value, even one whose bytes spell a number; padded text such as `" 5 "`; and a decimal such as `5.5`. No longer reported: `!!str 7`, which is the text `"7"`.
- **A "violation already on disk; kept" warning now carries the rule of the row it keeps** (`range` for `importance`, `enum` for `lifecycle`, `required` or `format` for an event's `date`), where it always said `model_validation`.
- **`pyrite qa validate` now flags a non-whole importance it finds in the index.** It uses the same rule, so a real `5.5` stored in the index, for example by an update before this release, is now reported.
