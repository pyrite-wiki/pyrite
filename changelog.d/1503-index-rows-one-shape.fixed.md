- A field now has one JSON type whichever reader returns it, and a value read and written back leaves the file as it was. `metadata` is always an object and `aliases` always a list. They used to be JSON text on MCP `kb_find_by_status`, `kb_find_by_assignee`, `kb_find_overdue`, `kb_find_by_location` and `kb_search` (keyword and semantic legs), on `pyrite search --fields '*'` and REST `/api/search` with `fields=metadata`, and on the REST folder-collection route (`aliases` only). A NULL `metadata` reads `{}`. A field the type declares and keeps in `metadata` (a backlog item's `rank`) is read at its own name on those readers too. A column field the KB declares as a `number` or a `checkbox` in `kb.yaml` (`priority`, `status`, `assignee`, `due_date` ...) reads as a number or a boolean on every index reader and on the single read (`kb_get`, `pyrite get`, REST `/api/entries/{id}`), where all of them used to return text such as `"7"`. Sending that value back through `kb_update` used to rewrite `priority: 7` as `priority: "7"`; it no longer changes the file. A task's `priority` is not declared a number where the schema reads declarations (`KBSchema.type_fields`), so it still reads as text (`"7"`) on every index reader and on `kb_get` alike; the `task_*` tools return it as an integer. Limit: the index cannot tell `7` from `"7"`, so a quoted number in a field declared a number reads as a number (the file keeps its quotes). (#1503)
