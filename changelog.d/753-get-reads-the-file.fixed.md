- **A single-entry read returns what the entry's file holds now, on every surface (#753).** `pyrite get`, `pyrite-read get`, REST `GET /api/entries/{id}`, MCP `kb_get` and `kb_read_body` read the file instead of the index row, so a hand edit, another tool's edit or a `git pull` shows up before the next `index sync`, and a `get` followed by `update --body-file` no longer drops a section written by hand. Body, title, tags and every frontmatter field come from one parse of the file; links, backlinks and `indexed_at` stay the index's. The read carries `content_hash`, the SHA-256 of the bytes it read (ADR-0042 decision 9). An entry whose file is gone, now holds another id, or cannot be parsed (a YAML typo made by hand) answers not-found -- `NOT_FOUND` from `get` and MCP `kb_get`/`kb_read_body`, 404 from REST -- where the index's old copy was returned before; #777 will give an unparseable file its own error code. REST export (`GET /api/entries/export`) reads each entry this way, so it now leaves out entries whose file is missing or unparseable instead of exporting the index's copy. REST `GET /api/entries/{id}` also carries `content_hash`; list routes that return the same shape from index rows carry `"content_hash": null`, meaning not computed for a list result. Thanks to @sb123sb123, whose #754 found the CLI case and its regression test. An update that echoes a read taken before a hand edit now writes over that edit, because the echo is compared with the file, not the stale row; `kb_update` does not check `content_hash` yet (ADR-0042 decision 11).
