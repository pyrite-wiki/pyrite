## 2026-11-16 · two-person team on one machine: auth on, two users, per-KB grants, one MCP-over-HTTP agent each · claude-sonnet-5-5
**Command:** (all with the isolation env; server `pyrite serve --host 127.0.0.1 --port 58431` with `PYRITE_AUTH_ENABLED=true`)
`pyrite init -t research -p work/team-notes -n team-notes --no-examples` (and `private-a`); hand-edited `default_role: write` / `default_role: none` into `$PYRITE_DATA_DIR/config.yaml`; `pyrite-admin user create root --role admin --password ...` (plus alice, bob as `write`); `curl -X POST /auth/login`; `curl -b root.jar -X POST /api/kbs/private-a/permissions -d '{"user_id":2,"role":"write"}'`; Python `mcp.client.sse.sse_client("http://127.0.0.1:58431/mcp/sse", headers={"Authorization": "Bearer <token>"})`.
**Expected:** a documented way to give each user's agent its own credential, then per-user KB visibility over `/mcp`.
**Got:** it works, but only by a route the docs never name (Friction 1). Alice's agent created/searched in both KBs. Bob's agent saw only `team-notes`, could edit Alice's entry there, and got `KB_NOT_FOUND` on `private-a`. Anonymous caller got 401 everywhere.

**Friction 1 — nowhere do the docs say how a *user's* agent authenticates over MCP-over-HTTP.** `docs/gemini-mcp-integration.md` and `docs/openai-mcp-integration.md` say "every request needs `Authorization: Bearer <key>` or `X-API-Key: <key>`", but "key" means an operator API key (`PYRITE_API_KEY` / `api_keys`), which carries a role, not a user. `docs/rest-api.md` says user accounts use "a key, or the `pyrite_session` cookie from `POST /auth/login`". The web UI's "My API Keys" turns out to be LLM-provider keys, not Pyrite credentials (`/auth/api-keys/{provider}`). What I did: guessed that the session cookie value works as a Bearer token. It does (`Bearer 5yZZ...` gave 97 tools and the right user's view). I found no doc that blesses this, and a 7-day cookie as a long-lived agent credential has no revoke or rotate story I could find. Severity: blocked-until-guessed. Would have helped: a "connect an agent as user X" section naming the credential (and its lifetime, how to mint a non-cookie one, how to revoke it).

**Friction 2 — the transport the task asked for is SSE, and that is only discoverable inside the Gemini/OpenAI pages.** README and getting-started show only stdio (`pyrite mcp --tier ...`). The HTTP mount is `GET /mcp/sse` + `POST /mcp/messages/`; `/mcp` itself answers nothing. The OpenAI page says streamable-HTTP clients (Codex `url`) cannot connect directly. A Claude Code user who tries `claude mcp add --transport http .../mcp` would hit that wall with no hint on getting-started. Severity: slowed. Would have helped: an "MCP over HTTP" section in getting-started or configuration (transport, URL, auth header, which tier the HTTP mount runs at).

**Friction 3 — which tier does the HTTP mount run at?** A `write`-role user's agent saw 97 tools with no `kb_registry_add`/`kb_push` in the list, yet calling `kb_registry_add` returned a normal result `{"error":"Tool 'kb_registry_add' requires the admin tier.","error_code":"FORBIDDEN",...}` with `isError: false` and a message "Tool 'kb_registry_add' not listed by server, cannot validate any structured content" from the client library. Tier follows the user's role (good), but I had to infer it. Same for every refusal below: the MCP `isError` flag is false for `KB_NOT_FOUND` and `FORBIDDEN`, so an agent framework that branches on `isError` treats refusals as success. Severity: annoyed (agents must parse `error_code`).

**Friction 4 — per-KB grants are REST-only and the request body is not in the docs.** configuration.md says "there is no CLI command for them yet". The OpenAPI body schema for `POST /api/kbs/{name}/permissions` is an unexpanded `$ref`; my first guess `{"user_id":2,"role":"write"}` worked, my second (`{"username":"alice",...}`) got 422 `missing body.user_id`, so the user id has to be looked up from `GET /auth/users` first. `default_role` has no CLI/REST setter either: I edited `config.yaml` by hand while the server was down. Severity: slowed.

**Friction 5 — `docs/web-ui.md` contradicts configuration.md on where a non-admin's write lands.** web-ui.md "Changes by non-admin users": "a signed-in user who is not an admin never writes to the main KB... a git worktree on the branch `user/<username>`". Observed: Bob (global role `write`, not admin) updated `standup-plan` over MCP and the change went straight into `team-notes/notes/standup-plan.md` (landing default `canonical`, KB not in git). configuration.md's `landing` section is the accurate one. Severity: annoyed; a reader of web-ui.md expects review isolation they do not have.

**Friction 6 — `pyrite init -t research` registers the KB as `type: generic`** (`pyrite list` and config.yaml show `kb_type: generic`), though the init output lists research entry types. Cosmetic/unclear whether the type matters. `PYRITE_CONFIG_DIR` was silently unused because `PYRITE_DATA_DIR` wins (this is documented, but I set both as told and the config dir stayed empty).

**Friction 7 — authorship is not recorded.** Search/get results for entries created by Alice and edited by Bob show `"created_by":null,"modified_by":null`, and the file has no author field. For a two-person team that wants to know who changed what, there is nothing in the entry (git was not set up, so no history either). Severity: annoyed.


**Refusal wording (Bob reading Alice's private KB):** `kb_get` / `kb_create` on `private-a` -> `{"error":"KB 'private-a' not found","error_code":"KB_NOT_FOUND","retryable":false,"suggestion":"To list the KBs you can read, call kb_orient (MCP) or `pyrite orient` (CLI) with no KB name.","legacy_error_code":"NOT_FOUND","did_you_mean":[]}`. `kb_list` hid it; `kb_search "zebra"` returned 0 results with no hint. Identical to a nonexistent KB, which is a sound way to avoid confirming existence, and `did_you_mean` was empty (did not leak the name). REST gives the same as 404 with a `detail` object. Anonymous: `GET /api/kbs`, `/mcp/sse` and `Bearer garbage` all `401 {"detail":"Invalid or missing API key"}` (anonymous tier unset). That message says "API key" to someone who is meant to sign in.

**Had to figure out:** Bearer = session cookie value; user ids from `GET /auth/users`; permissions POST body; that `default_role` lives only in config.yaml; SSE not streamable HTTP; first admin must come from `pyrite-admin` (this one is well documented).

**Worked well:** `pyrite-admin user create --help` pointed straight at the first-admin step; the startup warning about open registration named the exposed KB; the `default_role: none` + per-KB grant model behaved exactly as configuration.md says over MCP (hidden from `kb_list`, `kb_search`, `kb_get`); error JSON carried `error_code` and a suggestion.

**Severity:** slowed (overall; Friction 1 would block an operator who does not guess the Bearer-session trick)
