Git operations service using subprocess. Provides commit log, diff, blame, push, clone, pull, fork, and PR creation. Deliberately avoids gitpython/pygit2. Stateless class with all `@staticmethod` methods.

Used by version history endpoint, kb_commit/kb_push MCP tools, CLI git commands, ExportService (export-to-repo), and RepoService (subscribe, fork, sync). See [[collaboration-services]] for full method listing.

**One network-git constructor (ADR-0052 N2).** Every clone, pull and push is built by `GitService._network_plan(urls, token=, allowed_hosts=, credentials=, kb_name=, allow_userinfo=, registered_remote=, proxy=)`, in this order: (1) the host rule, every URL git will contact (after `insteadOf`, from `_effective_url` or `git remote get-url --all [--push]` in `_remote_plan`) on a host in `git_allowed_hosts` (`None` is the default, `github.com`, on every operation, push included), over https, or over ssh (`ssh://` or `user@host:path`, parsed by `_endpoint`) only when the operator's credential for that host is an `ssh_key`; refused with `RemoteNotAllowedError` before git runs; (2) the transport guards: `GIT_ALLOW_PROTOCOL` set to that one protocol, LFS transfers off, no terminal prompt, and the commands pass `http.followRedirects=false`; (3) the credential, in D3 order: the caller's own token when every URL is https on GitHub, else, for a network caller only (D-U6), the operator's `git_credentials` entry chosen by host, transport (a token for https, an `ssh_key` for ssh), KB (the KB's own first, never another KB's) and scope (`_operator_credential`: `registered_remote=True` for a registered KB's configured remote, from `ExportService.push_kb` and `RepoService.sync`; otherwise only an entry whose `url_prefixes` cover every URL by whole path segments, never a path with any `%` (remote or prefix), `_under_prefix`, D-U1), else none. For a network caller the plan also sets `http.proxy` to `git_proxy` or resets it (D-U2). A token reaches git through the inline helper scoped to its origin (`credential.https://host.helper=!f() { ... }; f`, answering `get` from `PYRITE_GIT_TOKEN`/`PYRITE_GIT_USERNAME`, every other helper reset); an ssh key, refused at build time if the file is missing or unreadable, through `GIT_SSH_COMMAND` = `ssh -F /dev/null -i <key> -o IdentityFile=none -o IdentitiesOnly=yes -o IdentityAgent=none -o UserKnownHostsFile=<known_hosts> -o GlobalKnownHostsFile=/dev/null -o StrictHostKeyChecking=yes -o BatchMode=yes`. The plan becomes the command's environment only through `_network_git_env(plan)`, which refuses a plan without `_PLAN_SEAL` (held by `_network_plan` and `_exempt_plan` alone; `tests/test_kb_repo_git_commands_are_hardened.py` checks no other code names it, builds a plan or `_replace`s one). `push(operator_push=True)` (from `ExportService.push_kb`) is exempt from the host rule only when `acting.is_local_process()` (the operator's `pyrite kb push`); over REST and MCP it is held to the rule like everything else (D2). `check_remote_allowed` remains the URL-string check for callers that validate before cloning (export, `add_remote`).

**Whose environment.** `git_hardening.git_env(hooks=)` decides from the reach itself; no caller passes isolation in. The local process gets its own environment (minus a parent git's repo-scoped variables). A network caller's git, for every command (status, log, commit and worktree as much as clone and push), gets only `NETWORK_ENV_ALLOWLIST` (`PATH`, `LANG`, `LC_*`, `TZ`, `TMPDIR`, and the CA-bundle variables), Pyrite's own `HOME`/`XDG_CONFIG_HOME` and `GIT_CONFIG_GLOBAL` (a file holding only the identity fallback and the account's `safe.directory` entries, `_network_gitconfig`), `GIT_CONFIG_SYSTEM=/dev/null`, empty `GIT_ASKPASS`/`SSH_ASKPASS`, `credential.helper=` and `core.askPass=` on the command line, and a closed `GIT_SSH_COMMAND`. OpenSSH reads `~/.ssh` through the passwd entry, not `$HOME` (verified in the T1a spike), so overriding HOME never closed identities: the ssh command line does. The repository's local config is still read. Commits for a network caller carry `git_identity`, written into Pyrite's own global config (`_git_env(identity=)`, `network_home(identity)`), so a repository's own `user.*` wins (D-U5); unset, the account's global identity is carried there until 0.27.0. `RepoService._get_token` and `UserService.get_current_user(token=)` hand a network caller only its own token, never the operator's stored CLI token, for git and for the GitHub identity lookup alike. GitHub API clients come from `pyrite/utils/egress.github_client(proxy=)`: `trust_env=False` and `git_proxy` for a network caller (`tests/test_http_clients_borrow_nothing.py`). `tests/test_network_git_gets_only_the_operator_credential.py` holds these against real git.

Nothing is written to disk, and the token is not in argv, a remote URL or a config file. `PYRITE_GIT_TOKEN` does travel in the git child process's environment, which other processes running as the same user can read. `_sanitize_output` redacts the raw token string only (an encoded or partial form is not matched); `sanitize_error` adds absolute-path redaction for text a caller sees. `scrub_remote_credentials` removes userinfo from the https GitHub remote URLs of a workspace, and only of a repository whose top level is that workspace folder (`_is_repository_root`: a folder with no `.git` of its own, inside another repository, is left alone); each key is rewritten with `--replace-all` first, so a failed step never leaves a remote with no URL. `pull` and `push` call it, and `RepoService.scrub_workspace_remotes` runs it over every registered workspace when the REST server or the MCP server starts and from the repo commands.

**Repository programs.** Every git process Pyrite starts takes its environment from `pyrite.utils.git_hardening.git_env` (via `_git_env`, or `_network_git_env` for a network command): `GIT_CONFIG_PARAMETERS` (what `git -c` sets, so it works on every git version) carries `core.fsmonitor=false` and `core.hooksPath=/dev/null`, and any inherited `GIT_CONFIG_PARAMETERS`/`GIT_CONFIG_COUNT` is dropped. Pyrite's diffs pass `--no-ext-diff --no-textconv`. Only `GitService.commit(run_hooks=True)` -- reached by the operator's own `pyrite kb commit` -- keeps the repository's commit hooks, so a hook that rejects the commit still fails that command; commits from REST and MCP run none. Filters (git-lfs), merge drivers and `gpg.program` are not guarded: Pyrite trusts a repository's local config as git does. `tests/test_kb_repo_git_commands_are_hardened.py` finds every subprocess call that starts git and fails on any `env=` that is not a bare constructor call (`git_env`/`_git_env` with at most `hooks`, or `_network_git_env(plan)` in the git service), and on any read of `os.environ` in the git service; one planted violation per shape proves the scan.
